# 桌面附件

聊天输入框的“添加文件”支持多选文件、从文件管理器复制后粘贴，以及拖入文件。截图和浏览器复制图片仍使用原有图片预览。普通文件显示名称、大小和移除按钮；文件可以单独发送，也可以与文字和图片混合发送。普通文字粘贴继续使用编辑器原有行为。

每轮最多 8 个附件，合计 20 MiB；普通文件每个最多 10 MiB。图片仍限制为 PNG、JPEG、GIF、WebP，最多 4 张、每张 5 MiB、图片合计 12 MiB，并由后端验证真实格式和尺寸。没有视觉能力的模型可以接收普通文件，图片仍要求模型声明支持图片输入。

## 传输与模型输入

`run.start` 保留 `images: [{data, mime_type}]`，新增可选 `files: [{name, mime_type, data}]`。文件数据为规范 Base64，不接受客户端指定本地路径或远程 URL。前后端均检查数量和大小，后端额外检查名称与编码。

Runtime 在项目目录之外的应用附件目录为每次发送创建独立副本，使用生成的文件名避免覆盖同名文件。文件元数据为 `{name, mime_type, size, path}`。保存副本失败会拒绝发送，输入框保留原草稿。

UTF-8 文本和代码提供每个文件最多 32 KiB、每轮合计最多 64 KiB 的摘录，并附完整副本路径。二进制文件只提供文件引用；PDF、Word 等内容需要适当工具读取，不把二进制解码为乱码，也不宣称供应商支持原生文档输入。摘录及引用作为独立的 `<attached_file>` 文本块进入模型上下文，不改变工具权限或 Plan 状态。

## 历史与生命周期

`run.started.files` 仅返回文件元数据；`UserMessage.attachments` 保存相同元数据，旧会话缺少该字段时按空附件读取。JSONL 不再保存一份普通文件的 Base64；图片仍沿用已有格式。桌面端把已匹配元数据的附件上下文块显示为文件卡片，普通用户正文保留。

文件副本与历史记录一起保留，正常结束任务不会删除历史引用的文件。尚未被消息接收的暂存副本会在失败或取消时清理。任务运行、归档和 Plan 的既有门禁保持不变。

会话切换清空待发送附件，迟到的文件读取不会进入新会话。读取期间暂停发送；发送被拒绝或运行失败时恢复附件，以便用户重试。Windows 原生粘贴直接使用 Chromium 提供的 `File` 对象，不新增通用文件系统 IPC 或依赖。
